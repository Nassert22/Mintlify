## نقطة البداية: ما هو موجود اليوم

| الطبقة | الواقع الحالي |
|---|---|
| الواجهة | React 19 + Vite + TypeScript، تسع شاشات حسب الدور (HR، المركبات، المستخلصات، التحويلات، المستخدمون، المساعد الذكي، الملف الشخصي) |
| البيانات | Firebase مباشرة من المتصفح (Auth، Firestore، Storage) بهوية المستخدم؛ الحاجز الأمني هو `firestore.rules` و `storage.rules` |
| الخادم | `server.ts` (Express على Cloud Run) بمسارين: `/api/chat` إلى Gemini و `/api/admin/users/email` إلى Identity Toolkit |
| الذكاء الاصطناعي | `AIAssistantApp.tsx`: أدوات تُنفَّذ في المتصفح بصلاحيات المستخدم نفسه |
| التوثيق | CLAUDE.md، HANDOFF.md، DEPLOY.md، DESIGN.md |

<Note>
هذا الأساس جيد لمستوى Expert لأن **الصلاحيات الدنيا مفروضة بالبنية** (المساعد لا يستطيع أكثر مما يستطيعه المستخدم). ما ينقصه هو ما تقيسه الشارة: تقييم منهجي، مراقبة، نموذج ML حقيقي، حوكمة موثقة، وأداء مقاس.
</Note>

## ربط المجلدات بالمجالات ومعايير القبول

<Steps>
  <Step title="D1 — أسس البيانات و ML (17.3%): مجلد ml/">
    اختر حالة استخدام واحدة من بياناتك الفعلية. الأنسب هنا: **توقع تأخر/رفض المستخلصات** (لديك سجل قرارات اعتماد/رفض/تأجيل جاهز كـ labels) أو **كشف التحويلات الشاذة**.
    - تقسيم زمني، `Pipeline` بلا تسريب، PR-AUC مع threshold مضبوط بتكلفة الخطأ.
    - **القبول:** تقرير تقييم يشرح المقياس، وتحليل أخطاء حسب المقاول/القسم.
  </Step>
  <Step title="D2 — DL/GenAI (16.7%): server/ai/rag و agent و evals/golden">
    - RAG على سياسات الشركة ولوائح HR وأدلة المركبات، بـ embedding يدعم العربية، hybrid retrieval، reranker.
    - الأدوات المعرّفة بـ zod في `src/ai/tools` وحلقة agent بحد أقصى للخطوات.
    - **القبول:** Context recall ≥ 0.85، Faithfulness ≥ 0.85، دقة اختيار الأداة ≥ 0.9 على المجموعة الذهبية.
  </Step>
  <Step title="D3 — هندسة البرمجيات (14.0%): server/ و tests/ و CI">
    - `server.ts` يتحول إلى `server/` بطبقات وعقود zod وأخطاء واضحة (400/422/429/503).
    - Streaming لـ `/api/chat`، timeouts، retries مع backoff، circuit breaker على Gemini.
    - **القبول:** اختبارات وحدة لا تستدعي LLM، CI أخضر، `pip-audit`/`npm audit` نظيف، لا أسرار في الصورة.
  </Step>
  <Step title="D4 — MLOps/LLMOps (18.0%): prompts/ و monitoring/ و evals.yml و deploy.yml">
    - الـ prompts ملفات مُصدَّرة، كل استجابة تُسجَّل مع إصدار الـ prompt والنموذج.
    - Tracing لكل طلب (Langfuse أو OpenTelemetry)، dashboard للتكلفة والزمن وعينة جودة يومية.
    - Drift على مدخلات نموذج المستخلصات، pipeline إعادة تدريب بـ gate.
    - **القبول:** runbook يشرح rollback خلال 5 دقائق، وeval يفشل الـ CI عند تدهور faithfulness.
  </Step>
  <Step title="D5 — المعمارية والأداء (12.6%): router.ts و cache.ts و tests/load">
    - قِس p95 لـ `/api/chat` بـ k6، ثم أضف caching و routing (نموذج أصغر للاستعلامات البسيطة) وقارن.
    - وثّق التدفق الحالي (المتصفح ← Firestore مباشرة، الخادم استثناء) وبرر كل مكون في `docs/architecture.md`.
    - **القبول:** جدول قبل/بعد، وتقدير تكلفة شهرية لـ 100 ألف طلب.
  </Step>
  <Step title="D6 — المسؤول والأمن والحوكمة (14.7%): guardrails/ و approval/ و evals/redteam و docs/">
    - **أهم نقطة في مشروعك:** أدوات المساعد تعمل بصلاحيات المستخدم، فحقن غير مباشر عبر مرفق مستخلص ملوث قد يجعل المساعد ينفّذ إجراءً (تحويل، اعتماد) نيابة عن مستخدم مخوّل. الحل: `approval/` يفرض موافقة صريحة على كل أداة مُعدِّلة، و`injection.ts` يعامل محتوى المرفقات كبيانات غير موثوقة.
    - PII redaction قبل أي إرسال إلى Gemini (أسماء، إقامات، أرقام حسابات) وفق نظام حماية البيانات الشخصية.
    - Model Card لنموذج المستخلصات + SHAP + تدقيق عدالة بين المقاولين.
    - **القبول:** نسبة نجاح هجمات `evals/redteam` بعد الدفاعات أقل من 10%.
  </Step>
  <Step title="D7 — الأعمال (6.7%): docs/business-case.md و README">
    - القيمة الكمية: ساعات موفرة في معالجة المستخلصات، تقليل التأخير، تقليل التصعيدات.
    - KPIs بمواعيد قياس، TCO يشمل تكلفة Gemini شهريًا، kill criteria.
    - **القبول:** ملخص تنفيذي 150 كلمة يفهمه مدير المزروعي بلا شرح.
  </Step>
</Steps>

## ترتيب التنفيذ المقترح

الترتيب مبني على الاعتماديات لا على الأوزان: لا يمكن قياس شيء قبل وجود tracing وevals.

| الأسبوع | العمل | المجالات |
|---|---|---|
| 1 | `server/` بطبقات + zod + اختبارات + CI | D3 |
| 2 | `prompts/` + tracing + `evals/golden` + `evals.yml` | D4, D2 |
| 3 | RAG على سياسات الشركة + reranker + تقييم | D2 |
| 4 | `approval/` + guardrails + `evals/redteam` | D6 |
| 5 | `ml/` نموذج المستخلصات + تقييم + Model Card + SHAP | D1, D6 |
| 6 | drift + retrain pipeline + runbook + canary deploy | D4 |
| 7 | k6 + cache + router + `docs/architecture.md` | D5 |
| 8 | business case + README + مراجعة شاملة | D7 |

<Tip>
**قاعدة واحدة:** كل أسبوع ينتهي بشيء قابل للقياس مدمج في `main`. لا تفتح المجال التالي قبل أن يمر الحالي عبر CI. هذا بحد ذاته تدريب على D4.
</Tip>
